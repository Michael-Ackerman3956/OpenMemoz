The one-sentence version

WebMCP is a browser API that lets your existing page hand an agent a list of typed functions to call, instead of making the agent guess its way through your DOM.

Correcting the mental model

Not PWA + MCP. There is no MCP server, no transport to configure, and no PWA requirement.

What it is not
✗ A PWA requirement — a single static HTML file qualifies
✗ An MCP server you host, start, or register
✗ A chat UI you have to build — the agent is the browser's
✗ An LLM you supply, pay for, or choose
✗ A rewrite — it is an additive progressive enhancement
What it is
✓ One browser object: document.modelContext
✓ Your page declares typed tools at runtime
✓ Whatever agent drives the browser discovers and calls them
✓ Tools run in the page, in the user's session
✓ The human watches it happen in the real interface
The whole loop
Page registers tools→ Agent reads the list→ Agent calls one→ Your JS runs, UI updates
Why the standard exists — Chrome's own framing

The alternative is actuation: the agent scrapes the DOM, guesses which button is "checkout", and clicks. Every step is open to interpretation and silently breaks when you restyle. With WebMCP the site declares the element's purpose, so it gets used correctly. Chrome's stated benefits: higher task-completion accuracy, fewer steps, tokens spent on the task rather than on navigation, and your brand and human-centred design left intact.

So your instinct was right, with one correction. It is "a website that does something" — but the something must be an operation your app already performs, re-exposed as a typed function. Small is fine. Vague is not.
Sources: developer.chrome.com/docs/ai/webmcp · learn.chatgpt.com/docs/sites (Site tools)

WebMCP vs MCP

Same tool shape, different attachment point. A site can support both — and for MailPidge, that distinction decides the whole strategy.

MCP serverWebMCP / Site tools
Lives inA local or remote server processThe open page, as JavaScript
Needs a page open?No — works headless, independent of any tabYes — tools die when you navigate away
Setup by the userInstall / connect / authorize a serverNone. Just visit the site
Identity usedServer credentials you provisionThe visitor's existing signed-in session
Human visibilityOpaque — results arrive as textRuns in the real UI; the user watches
Best whenBatch work, automation, no UI neededYou and the agent must see the same thing
The shared type system
Cloudflare's bridge uses MCP's own Tool and CallToolResult types verbatim. An agent that already speaks MCP can drive a page with nothing added. "The browser is just another place MCP runs."
Why that matters to you
MailPidge's roadmap already has Worker /mcp as the sole MCP server. WebMCP is not a competing plan — it is the same tool contract, surfaced one layer up. Design the tools once.
OpenAI's phrasing is the clearest test: use WebMCP "when you and the agent need to see the same thing, such as when editing a canvas or exploring a dashboard." A campaign console being driven while you watch the progress bar is exactly that shape.

The real API surface

Verified against Chrome's Imperative API docs, last updated Aug 20 2026. This is the whole thing.

// The minimum viable WebMCP tool — OpenAI's own starter example.
// The support check is mandatory: it keeps every other browser working.
if (typeof document.modelContext?.registerTool === "function") {
  await document.modelContext.registerTool({
    name:        "get_page_title",
    description: "Read the title of the current page.",
    inputSchema: { type: "object", properties: {}, additionalProperties: false },
    annotations: { readOnlyHint: true },
    execute:     async () => ({ title: document.title }),
  });
}
Everything else on modelContext
registerTool(t, {signal})Add a tool. Abort the signal to unregister.
getTools()Alphabetical list of authorized tools.
executeTool(t, jsonStr)Call one manually. Returns the result.
"toolchange" eventFires when the available set changes.
Details that bite
execute(args, { signal }) — second arg carries an AbortSignal. Pass it to fetch or the agent cannot cancel.
Origin-isolated only — sending Origin-Agent-Cluster: ?0 disables WebMCP entirely.
Permissions Policy tools — defaults to self; cross-origin iframes need allow="tools".
Chrome 153+ unregisters without killing in-flight calls.
Imperative API
Plain JS. Full control. What every real example below uses.
Declarative API
Add toolname / tooldescription attributes to an HTML <form>. Zero JS.
Framework hooks
React useWebMCP · Angular Signal Forms · webmcp-types for TS typings.
Two annotations carry the safety contract: readOnlyHint and untrustedContentHint. They are hints to the agent, not enforcement — see slide 10.
Source: developer.chrome.com/docs/ai/webmcp/imperative-api · learn.chatgpt.com/docs/sites

What their code actually does

Four patterns worth copying verbatim. All four are things you would not guess from the spec.

1 · One AbortController unregisters everything
// components/webmcp-tools.tsx — a client component
useEffect(() => {
  const { modelContext } = document;
  if (typeof modelContext?.registerTool !== "function") return;

  // Aborting unregisters every tool on unmount.
  const controller = new AbortController();
  const options = { signal: controller.signal };

  void Promise.all([
    modelContext.registerTool({ /* … */ }, options),
    /* … three more … */
  ]);
  return () => controller.abort();
}, []);
2 · A hard output budget, enforced by measurement
// lib/webmcp/action.ts — "use server"
const MAX_OUTPUT_CHARACTERS = 1_450;

// Add items one at a time; stop before the budget blows.
function fitItemsToOutputBudget(items, buildOutput) {
  const included = [];
  for (const item of items) {
    const candidate = buildOutput([...included, item]);
    if (JSON.stringify(candidate).length > MAX_OUTPUT_CHARACTERS) break;
    included.push(item);
  }
  return buildOutput(included);
}
3 · Schema loosely, Zod strictly — twice
// Declared in inputSchema for the agent…
productHandle: { type: "string", maxLength: 255,
  pattern: "^[A-Za-z0-9][A-Za-z0-9-]*$" }

// …and re-validated server-side, because schema is a hint.
const productHandle = z.string().trim().min(1).max(255)
  .regex(/^[A-Za-z0-9][A-Za-z0-9-]*$/);

if (!parsed.success)
  return toolError("INVALID_INPUT", "…did not match the tool schema.");
4 · A typed error vocabulary the agent can act on
type WebMCPErrorCode =
  | "INVALID_INPUT"
  | "NOT_ALLOWED"
  | "NOT_AVAILABLE"
  | "NOT_FOUND"
  | "UPSTREAM_UNAVAILABLE";

// Returned as data, not thrown — so the model can self-correct
// and retry with valid parameters instead of giving up.
{ error: { code, message } }
Also worth stealing: tool titles come from next-intl translations, and every returned string is squeezed through a conciseText() truncator (titles to 80 chars, variants to 48). Output discipline is treated as a first-class concern, not an afterthought.

Example 2 — OpenAI's own apps

The showcase entries are small, single-purpose apps. Roughly 10 tools each is the observed norm.

WanderNote — collaborative trip planner · 11 site tools · built with Codex + Sites

"Plan an hourly itinerary and map with an agent. Edit or dismiss suggestions, leave comments, and export as PDF." The stated WebMCP rationale: the agent turns plans from connected apps into an itinerary, then reads your comments and revises the trip — collaboration stays tied to the schedule and map you can see and edit.

Hosted at wandernote.openai.chatgpt.site — a ChatGPT Sites deployment. Sibling entries: Codex Modeling Studio (3D scenes), Crossword Desk, Fieldwork //12 (browser beat machine).

OpenAI's documentation site — the tool set you can inspect live
search_openai_docsSearches the documentation.
lookup_pageReads a page by path or URL.
lookup_contextReads the current route and the user's selected text.
navigate_to_pageOpens a matching page on the current site.
generate_custom_guideStarts an async build and returns status plus a link.

Note lookup_context — "reads the current docs route and selected text." A tool whose entire job is telling the agent where the human is looking. That is the WebMCP-native idea an MCP server structurally cannot offer.

OpenAI's stated recipe for adding it to an existing app

"Start with an operation your application already supports." Their three suggested shapes: a dashboard where the agent sets a date range and inspects the data behind a chart; a document editor where it finds a section, suggests an edit, or leaves a comment for review; a travel planner where it compares options and updates an itinerary while you watch the map. Then: "reuse the application's existing logic and permissions."

Read the guidance literally: keep inputs narrow, describe side effects, return enough to verify the result, reuse existing auth and validation, and preserve the normal interface for people and browsers without WebMCP.

Example 3 — Cloudflare's zero-code bridge

Directly relevant to you, and a trap. It gives any Cloudflare site WebMCP with a dashboard toggle.

<!-- Cloudflare injects this at the edge via HTMLRewriter. Same origin, HTML otherwise untouched. -->
<script type="module"
        src="/.webmcp/bridge.js"
        data-packs="c2pa,mcp-server-client"
        data-mcp-url="/mcp"></script>
How the Site MCP Server pack works

At boot the bridge calls tools/list on your same-origin /mcp, then registers a proxy tool for each one. Each proxy's execute() POSTs tools/call back to your endpoint with credentials: "same-origin" — so it runs as the logged-in visitor. If the browser has no WebMCP surface, the bridge returns and does nothing.

Operational facts
Enable: Dashboard → Agent Readiness → WebMCP
Verify: curl -s https://site | grep webmcp
Test without your own agent: point BrowserRun at the URL
Second pack: Content Credentials (C2PA) — scan_images_c2pa, inspect_image_c2pa
Every tool runs in-browser. No round trip to Cloudflare.
Why this is a trap for the challenge

If you build Worker /mcp and flip the toggle, MailPidge becomes WebMCP-enabled with zero lines of WebMCP code. Excellent engineering; almost certainly a losing submission. The rules score "meaningfully extended with WebMCP," and there would be no WebMCP work in your git history to point at. Worse, a generic proxy produces generic tools — no confirmation gating, no page-state awareness, none of the things that win on WebMCP Leverage.

Use it as the fallback, not the entry. It is also a strong argument for designing your tool contract once and exposing it deliberately.

Also confirms the honest read on browser support: Cloudflare says Chrome 146, experimental; Chrome's docs say the origin trial opens at Chrome 149; Devpost says Chrome 149+. For local work the flag is what matters — see slide 11.
Source: blog.cloudflare.com/webmcp (Aug 6 2026, Will Rowe) · developers.cloudflare.com/browser-run/features/webmcp

Chrome's best practices

These read like scoring criteria for the "WebMCP Leverage" judging axis. Treat them as such.

Tool strategy
One function per tool. Overlapping tools confuse the agent about which to pick.
No maximum tool count — but each one consumes context window and adds latency.
Static registration by default. Register dynamically only when a tool is genuinely unusable in the current page state.
Trust the agent. Don't script an exact step sequence; describe the capability.
Naming — the distinction they stress

Use verbs that describe exactly what happens, and separate execution from initiation:

create-event creates it, immediately
start-event-creation-process redirects to a form

Descriptions use positive language. Not "Don't use this for weather" — instead "This tool can create a calendar event, scheduled for a specific date and time." Limitations should be implicit in a good description.

Minimize cognitive computing
Accept raw input — take "11:00 to 15:00" as a string; don't make the model compute the delta. Declare concrete types and enums.
Explain the why
Natural language beats opaque IDs. shipping="Express", never shipping_id=1.
Validate strictly in code, loosely in schema
Schema constraints "are not guaranteed." Descriptive errors let the model self-correct and retry.
Reliability rules with teeth
Update the interface state after the function completes. Agents read the UI to plan the next step. If the function finishes before the UI catches up, the agent plans against stale state.
Fail gracefully on rate limits. Return a meaningful error or tell the user to do it manually.
Don't patch model quirks with narrow rules. Abstract the tool instead; make awkward fields optional and let the agent ask the user.
Correction to the previous version of this deck: it listed hard character budgets (500 description / 150 param / 30 name / 1.5K output) as "enforced." I could not find those numbers in the spec README, Chrome's docs, or OpenAI's docs. Vercel's 1_450 output cap is a self-imposed convention. Treat tight metadata as a strong practice, not a platform limit.
Source: developer.chrome.com/docs/ai/webmcp/best-practices (published May 18 2026)

The trust model

The platform's position is blunt: tool definitions and results are untrusted content, and annotations prove nothing.

OpenAI's exact framing

"A tool's name or claim that it only reads data isn't proof of what it does. Website instructions don't give the agent permission to share unrelated information or take sensitive actions." Each invocation gets a safety review before it runs, and normal confirmation policies still apply to consequential actions — sending messages, purchases, deleting data, changing permissions. "These checks reduce risk; they don't make a website or its output trustworthy."

Browser-level gates you must satisfy
Origin isolation required. WebMCP is disabled in documents with document.domain enabled, i.e. anything sending Origin-Agent-Cluster: ?0.
Permissions Policy tools, default self. Cross-origin iframes are off unless you add allow="tools".
Cross-origin exposure is opt-in twice — the host lists exposedTo, and the caller must ask via fromOrigins.
Users can switch it off at Settings → Browser → Permissions → Enable site tools.
What you are responsible for
Reuse the app's existing authentication and authorization — a tool is not a new privilege tier.
Re-validate every input server-side. The schema is advisory.
Mark reads with readOnlyHint: true and anything reflecting user or third-party text with untrustedContentHint: true.
Redact in the return value. Vercel returns a "redacted page" of the cart, not the cart.
Gate irreversible actions behind an explicit human confirmation.
Where this is an advantage for MailPidge

MailPidge already has the hard parts: an owner-only auth check, compliance gates gated twice, a suppression list that aborts the send if unreadable, HMAC-only persistence with no raw address anywhere, and sanitizeErrorSnippet() scrubbing address-shaped text out of error paths. A tool surface that cannot leak a recipient address even if the agent is adversarial is a genuinely strong story — and it is already true, not something you must build.

Chrome publishes a separate WebMCP tool security guide on prompt-injection risks and trust boundaries, plus security considerations for agent authors. Read it before writing a mutating tool.
Sources: developer.chrome.com/docs/ai/webmcp/secure-tools · learn.chatgpt.com/docs/sites §Security and user controls

MailPidge — the assessment

You do not need a new app. And the CE/Pro dilemma that stalled this rests on a false premise.

The premise to drop: "WebMCP means putting my AI features in CE"

WebMCP ships no AI. No model, no agent, no prompt, no LLM dependency, no API key. The agent belongs to the visitor's browser. What you add to CE is a tool-registration layer over API routes CE already exposes — the same category of thing as a keyboard shortcut. Pidge, the ADK agent, Gemini, Firestore, BigQuery and every other Pro concept stay exactly where they are.

Concretely, CE grows by roughly two files under packages/ui-ce or apps/pwa, zero new runtime dependencies, zero Pro concepts, zero Kernel changes. That is a Track 3 change. It does not widen the CE surface in any way you would regret.

Scale, measured against the closest precedent
Vercel storefront2 new files · 447 lines · 4 tools
WanderNote11 tools
OpenAI docs site5 tools
Margin10 tools

This is a two-to-three day piece of work on an app that already exists, not a rewrite. Your fear of building from scratch is unfounded.

Why MailPidge is a genuinely good fit
The console is one screen the human watches while a long job runs — exactly OpenAI's "you and the agent see the same thing" test.
Every operation you would expose already exists as a Worker route.
Auth, compliance gates, suppression and HMAC-only persistence are already enforced server-side.
The domain has a real, legible irreversibility boundary — which makes a deliberate refusal to expose Send a strong design story rather than a missing feature.
The two real risks — neither is technical
1 · Commit history in the public repo. Judging requires public, timestamped commits inside Aug 25 – Sep 3. Public CE is a materialization from tooling/publish-ce/public-paths.txt. If that produces one squashed commit, the "meaningfully extended" evidence is thin. Verify what history publish-ce actually emits before committing to this path — this is the first thing to check, not the last.
2 · Zero real sends, ever. The README says 0 emails sent, 0 deploys, 0 browser opens. A demo video of an agent driving a never-deployed system is the highest-variance part of this plan. Deploy and send to yourself on day one.
Verdict: build on top of MailPidge CE. Do not start a new app, do not expose Pro, and do not rely on Cloudflare's zero-code toggle as the submission.

React integration — two packages, pick one

Chrome's docs and Devpost link different packages. Both are real. Use the Chrome-maintained one.

use-webmcp-tool — use this
v0.2.0 · GoogleChromeLabs/use-webmcp-tool
"Maintained by Chrome, and will be updated with any spec changes."
Linked by Devpost as the official Google Chrome supporter resource.
React 18+ peer dep. ESM, TS types included, no runtime dependencies.
Feature-detects and degrades to a no-op where the API is absent.
usewebmcp — community
v5.0.1 · WebMCP-org/npm-packages
"Standalone React hooks for strict core WebMCP tool registration."
This is the one Chrome's Imperative API page links to.
Higher version number, but not Chrome-maintained.
The hook, and why it beats calling registerTool yourself
import { useWebMCP } from "use-webmcp-tool";

const { supported, registered, error } = useWebMCP({
  name, description, inputSchema, annotations, execute,
  enabled      // register only while true — mirrors page state for free
  formatOutput // shape the result before MCP normalization
  onError      // side effect when execute throws
});

// Registered on mount, unregistered on unmount. The tool list the agent sees
// stays in lockstep with what is actually on screen.
if (!supported) return null;
Return-value normalization — the part worth memorizing
a string{ content: [{ type: "text", text }] }
undefined / null{ content: [] }success, no payload
already {content}passed through untouched
a thrown value{ content: [...], isError: true }Error or not — throw "not signed in" counts
a returned Errortreated exactly like a throw

Their stated rule: "A failure must never read as success to the agent."

One error you will hit: the returned error surfaces NotAllowedError when a tools permissions policy blocks registration. Render that state rather than failing silently.

Part II · Why client-side at all

The spec's own case against backend integrations. Three named problems — and MailPidge has all three.

1 · UI disintermediation & context loss

"Backend integrations take place directly between the agent and the service, bypassing the service's web UI / browser experience." The user loses sight of what happened. → For a 3h42m send you cannot recall, the operator watching the console is the safety mechanism.

2 · Replication of state & auth

"Web developers must replicate the user's state, active context, and authentication credentials on a separate server." → MailPidge is single-tenant with one OWNER_EMAIL and one refresh token. A backend agent integration would mean a second identity path into the same sending account. WebMCP reuses the owner's live browser session instead.

3 · Developer burden

"Exposing a site's client-side capabilities requires writing a dedicated backend server, rather than reusing familiar client-side JavaScript." → This is the whole reason the CE/Pro problem dissolves. No new server, no new identity, no AI dependency in CE.

The spec's summary sentence, worth quoting in your submission

WebMCP "enables visually rich, cooperative interplay between a user, a web page, and an agent with shared context. Page UI and content remain available to the agent for actuation, but the agent can use WebMCP tools to achieve the user's goals more directly, reliably, and quickly."

One hard scope limit from the spec: WebMCP supports Tools only. The Resources and Prompts primitives from backend MCP do not exist here. Don't design around them.

The Declarative API, in full

Four HTML attributes turn a form into a tool — and one of them is the confirmation guardrail you need.

<form toolname="search-cars"
      tooldescription="Perform a car make/model search"
      toolautosubmit>
  <label for="make">Vehicle Make</label>
  <input id="make" name="make" required>

  <label for="model">Vehicle Model</label>
  <input id="model" name="model" required
         toolparamdescription="e.g., 330i, F-150">

  <button type=submit>Search</button>
</form>

The browser synthesizes the JSON Schema from the fields. <select> options become anyOf with const + title per option. Removing either toolname or tooldescription unregisters the tool.

toolautosubmit — the guardrail

Present: "the agent can submit the form without waiting for user interaction." Absent: the browser brings the form into focus, populates the fields, and leaves it visible — the human presses the button.

That is a platform-level "fill but don't submit" primitive. It is exactly the semantics MailPidge's Send needs, with no custom code.

Param description resolution order
1 · toolparamdescription
2 · the associated <label> textContent
3 · aria-description
Groups (radios): put it on the nearest <fieldset>.
Returning results to the agent without navigating away
form.addEventListener('submit', (event) => {
  event.preventDefault();
  const errors = myFormIsValid();

  if (errors.length) {
    // Only speak to the agent when the agent is the caller.
    if (event.agentInvoked)
      event.respondWith(Promise.resolve('Validation failed: ' + errors.map(e => `${e.field} (${e.message})`).join(', ')));
    return;
  }

  const resultPromise = performAsyncSearch(new FormData(event.target));
  if (event.agentInvoked) event.respondWith(resultPromise);  // no navigation
});
Two additions to the API surface: SubmitEvent.agentInvoked tells you whether a human or an agent submitted, and event.respondWith(promise) returns a structured answer instead of navigating. Accessibility stays intact because the form is still a real form.

Hard rules & anti-patterns

From Google's modern-web-guidance skill — the guidance Chrome ships for coding agents. Read as a checklist.

Do not do this
Do not use backend transports. No HTTP, no SSE, no stdio. "WebMCP is for browser tabs, not Node.js background processes."
Do not include Resources or Prompts. Not supported. Tools only.
Do not use unregisterTool. It does not exist. AbortSignal is the only mechanism.
Do not ship without parameter descriptions. Every property needs one, "to minimize agent hallucinations."
Do not use outside a Secure Context. HTTPS required.
Do not force flow control. No "don't call B after A" — let the agent decide.
When to discourage WebMCP entirely
High-risk actions without guardrails. "Avoid auto-submitting tools for destructive or irreversible actions (e.g., deleting data) unless the UI requires manual user confirmation outside the agent's control."
Hyper-dynamic state. "If data changes faster than the agent can react, it may work with stale context."

Read the first one twice. It is a direct instruction to do what MailPidge's design already implies: send is irreversible, so confirmation must live in the UI, outside the agent's reach.

The Tool Factory pattern — for passing app context into tools
export function createInventoryTool(inventoryManager) {
  return {
    name: "get_inventory",
    description: "Lists items in the inventory.",
    inputSchema: { type: "object", properties: {} },
    execute() { return inventoryManager.getItems(); },
    annotations: { readOnlyHint: true },   // convention: annotations after execute
  };
}
Sync vs async execute
async for network, IndexedDB, or waiting on a state change. sync for pure logic and localStorage. Don't make everything async by reflex.
It is still just client-side JS
"Keep secrets out of client-side code, access backend databases through secure API layers." A tool is not an exemption from ordinary web security.
Version floor, precisely stated: Chromium 146.0.7672.0 or higher with #enable-webmcp-testing — and Edge counts (edge://flags). That reconciles the Chrome 146 / 149 confusion: 146 is the flag floor, 149 opens the origin trial.

Note the description too: "currently visible… after all filters have been applied" — it tells the agent the tool is scoped to page state, not the whole dataset. That single clause prevents a whole class of wrong answer.

2 · dispatchAndWait — how to actually return after the UI updates
// Chrome's best practice says "return after the interface state updates".
// This is what that looks like in real code.
function dispatchAndWait(eventName, detail = {}, successMessage = "Action completed successfully", timeoutMs = 5000) {
  return new Promise((resolve, reject) => {
    const requestId = Math.random().toString(36).substring(2, 15);
    const completionEventName = `tool-completion-${requestId}`;

    const timeoutId = setTimeout(() => {
      window.removeEventListener(completionEventName, handleCompletion);
      reject(new Error(`Timed out waiting for UI to update (requestId: ${requestId})`));
    }, timeoutMs);

    const handleCompletion = () => { clearTimeout(timeoutId); resolve(successMessage); };
    window.addEventListener(completionEventName, handleCompletion);
    window.dispatchEvent(new CustomEvent(eventName, { detail: { ...detail, requestId } }));
  });
}

The tool fires an app event and does not resolve until the view acknowledges the matching requestId — with a timeout that reports honestly rather than hanging. For MailPidge, stage_campaign should resolve only once the console form visibly shows the staged values.
